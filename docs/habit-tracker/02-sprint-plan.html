NeverExpire V2 · Habit Tracker · Planning Package 2/10

🏃 Sprint Plan

15 one-week sprints across 4 phases. Story details in 03-user-stories.html · live status in 04-status-board.html.

🟢 Phase 1 — The Reliable Core Sprints 1–4

Sprint 1 — Backend foundation Phase 117 pts

Goal: the entire habit data layer exists, tested, behind a flag — before any UI is written.

Stories

HT-901 Feature flag habits_enabled (1) HT-101 Habit data model & migrations (5) HT-102 Habit CRUD API (3) HT-103 Check-in API + idempotency (3) HT-104 Streak engine + StreakState cache (5)

Technical notes

  • New tables: habits, habit_checkins, habit_streak_state (see research doc §15). user_id FK only — never person_id.
  • Blueprint routes/habits.py; repository + queries functions follow existing V2 layering. Envelope: {data, error}.
  • Streak rules (schedule-aware, freeze, repair, vacation) computed backend-only; unit tests cover every schedule type × miss pattern.
  • Idempotency: unique (habit_id, date, slot_index) — replayed offline check-ins are safe no-ops.
  • User timezone (IANA) added to the user profile; "a day" = local date.

Verification

  • pytest suite green (streak engine: ≥15 cases incl. weekly-quota + interval edge cases)
  • All endpoints exercised via REST client with JWT; 401/403/422 paths checked
  • Flag off → habit endpoints return 404-style disabled response
Exit: mobile team (Sprint 2) can build against a stable, documented API without backend changes.

Sprint 2 — Mobile habit core Phase 119 pts

Goal: create, see, and check in habits on the phone — the feature exists end-to-end (no reminders yet).

Stories

HT-105 Habits tab + list screen (3) HT-106 Create/edit habit screen (5) HT-107 Template gallery, ~40 habits (3) HT-108 Check-in interaction (3) HT-109 Offline queue + sync (5)

Technical notes

  • 3-layer rule: HabitsScreen → useHabits → habitService → ApiService. New routes in routes.js; colors from theme.js; category icons use the emoji icon system.
  • Templates ship as static JSON in the app (name, category, schedule preset, emoji) — one tap adds, then opens editor pre-filled.
  • Check-in = haptic + tick animation + streak count increment; this is the emotional core — budget polish time.
  • Offline queue in AsyncStorage; flush on foreground + connectivity change; server idempotency makes retries safe.

Verification

  • Variable-scope check on all new components; build + on-device render, clean console
  • Airplane-mode test: check in offline → reconnect → exactly one check-in on server
  • All 5 schedule types creatable and correctly displayed
Exit: Nadeem uses the tracker for real habits, daily, on his own phone (flag on for his account).

Sprint 3 — Reminders Phase 115 pts

Goal: excellent notifications — the load-bearing wall of the whole feature.

Stories

HT-201 Scheduling engine, rolling 48h window (8) HT-202 Actionable Done/Snooze notifications (5) HT-203 Quiet hours + per-habit mute (2)

Technical notes

  • expo-notifications local scheduling. iOS caps 64 pending — schedule a rolling 48h window, re-plan on app open/foreground; the re-planner is the 8-pointer.
  • Notification categories with Done/Snooze-30m actions; responses handled in foreground and background handlers; Done writes through the same check-in path (source: notification_action).
  • Android 13+ runtime notification permission asked in context (first reminder set), not at app start (part of HT-201 scope).
  • Quiet hours default 22:00–07:00; reminders falling inside shift to window edge or skip per user setting.

Verification

  • Device test matrix: app foreground / background / killed — Done action lands a check-in in all three
  • Create 10 interval habits → pending scheduled notifications stay under the iOS cap
  • Snooze fires 30m later; quiet hours respected across midnight boundary
Exit: a week of real reminders without a single missed or duplicated notification.

Sprint 4 — Dashboard, forgiveness & quotes Phase 120 pts (stretch)

Goal: the daily home screen — stats, streak mechanics, and warmth. Phase 1 ships at sprint end.

HT-401 Dashboard aggregate API (5) HT-402 Today strip (2) HT-403 Streak hero (1) HT-404 Consistency heatmap (2) HT-405 Category rings + period toggle (2) HT-406 Rule-based insight card (1) HT-301 Streak freeze UI (1) HT-302 Repair window UI (1) HT-303 Vacation mode UI (1) HT-501 Quote bundle (1) HT-502 Contextual quote placement (1) HT-902 Phase 1 E2E + metrics (2)

  • Visual reference: 05-visual-dashboard.html and 07-visual-streaks.html.
  • Metrics events (HT-902) logged from this sprint: creation, check-ins, permission grants, D7/D21 cohort retention.

🔵 Phase 2 — Intelligence Sprints 5–8

Sprint 5 — Questionnaire & profile Phase 210 pts

Goal: the conversational intake that produces the user_profile contract every AI call depends on.

Stories

HT-601 Questionnaire UI flow (5) HT-602 user_profile model + API (3) HT-603 Retake/update flow (2)

Technical notes

  • One-question-per-screen, tappable chips, progress dots, skippable at any point; ~3 minutes; branching prunes irrelevant questions.
  • Output: versioned user_profile JSON (goals ranked, constraints, chronotype, anchors, tone) — schema fixed in ai-prompts.md §1 before UI work starts.
  • Explicitly no medical-condition questions; health-context questions are lifestyle-only.
  • Lighter sprint on purpose — buffer absorbs Phase 1 gate fixes from tester feedback.

Verification

  • Complete, skip-half, and skip-all paths all produce valid (possibly partial) profiles
  • Retake overwrites with version bump; old version retained
Exit: profile JSON validated against the schema the AI planner will consume.

Sprint 6 — AI plan generation Phase 215 pts

Goal: profile in → reviewed, editable 3–5 habit plan out. Nothing activates without confirmation.

Stories

HT-701 AI plan endpoint, structured output (8) HT-702 Plan review UI (5) HT-706 AI cost metering (2)

Technical notes

  • POST /habits/ai/plan → Anthropic (server-side key, reuse extractor client patterns) with tool-use JSON schema; code-level validation of every field before anything reaches the UI (times sane, categories valid, ≤5 habits, no medication category ever).
  • System prompt = ai-prompts.md §2 verbatim — prompts live in a module, not inline strings.
  • Review UI: draft cards, accept-all / edit-any / reject; accepted cards create habits through the normal CRUD path.
  • This endpoint doubles as the text/voice parse endpoint later (S9) — design the request shape for both from day one.
  • Token metering per user per week with config alert threshold, from the first call.

Verification

  • Schema-invalid model output → graceful retry/fallback, never a crash or raw JSON on screen
  • Guardrail suite (ai-prompts.md §7) run against the plan endpoint: zero violations
  • 10 varied profiles → all plans have 3–5 habits with sane schedules
Exit: a new user can go questionnaire → AI plan → active habits in under 5 minutes.

Sprint 7 — Medication reminders Phase 213 pts

Goal: the most reliable, least intelligent part of the app — a dumb alarm with a checkbox, by construction.

Stories

HT-801 Category isolation + AI exclusion (3) HT-802 Reminder reliability: re-fire, exact alarms (5) HT-803 Adherence log + export (3) HT-804 Acknowledgment + missed-dose indicator (2)

Technical notes

  • HT-801 merges first: query-layer filter excludes medication habits from every AI input/output path — no prompt change can leak them. Landed before any coaching job (S8) exists.
  • Free-text label + times only. No drug database, no structured dosage — keeps the app out of medical-device territory.
  • Ignores quiet hours (user-overridable); re-fires once after 15 min unacknowledged; Android SCHEDULE_EXACT_ALARM asked in context, inexact fallback for ordinary habits.
  • No streaks, freezes, quotes, or gamification on medication items — plain taken/missed record; export as simple text list.

Verification

  • Grep-level + test-level proof: medication rows absent from every AI query fixture
  • Re-fire verified with app killed on both platforms; exact-time delivery on Android 14
  • Missed dose shows indicator text only — never advice ("see your notes", never "take it now")
Exit: medication reminders trusted enough to use for a real daily medication.

Sprint 8 — Adaptive coaching & guardrails Phase 213 pts

Goal: the weekly coach — one suggestion at a time, on the dashboard, never pushed. Phase 2 ships at sprint end.

Stories

HT-703 Weekly coaching job + suggestion cards (5) HT-704 Personalized encouragement lines (3) HT-705 Guardrail post-filters + audit log (3) HT-604 Periodic 3-question check-ins (2)

Technical notes

  • Weekly batch analysis (aggregates only, never raw health data) → at most one AiSuggestion card: move-time / level-up / reduce-load, with accept/dismiss. Accepting applies the change through normal CRUD.
  • Encouragement lines are stats-driven observations (Haiku-class model), replacing generic quotes where data allows; same off-toggle as quotes.
  • Post-filter (ai-prompts.md §6) rejects any output containing medical/dosage content; every AI response logged to an audit table with filter verdict.
  • Check-in questionnaire ("too easy / right / too much?") every 3 weeks feeds profile freshness.

Verification

  • Full guardrail suite green across plan + coach + encouragement endpoints
  • Suggestion accept → habit actually changes; dismiss → not re-suggested for 2 weeks
  • Phase 2 E2E on both platforms; audit log populated for 100% of AI calls
Exit: Phase 2 gate measurement starts (questionnaire-completer retention vs. skippers; zero guardrail violations).
🚧 Phase 2 gate: questionnaire completers retain measurably better than skippers · zero guardrail violations in the audit log · AI cost per active user within threshold.

🟠 Phase 3 — Senses Sprints 9–12

Sprint 9 — EAS dev-client & voice creation Phase 310 pts

Goal: leave plain Expo Go; speak a habit into existence with mandatory visual confirm.

Stories

HT-1001 EAS dev-client + expo-speech-recognition (5) HT-1002 Voice habit creation flow (5)

Technical notes

  • EAS build profiles (dev/preview) — one-time infra cost that unblocks all Phase 3 native modules. Nadeem handles Expo/Apple/Google account steps; Claude does config.
  • On-device/OS STT only — audio never reaches our servers. Mic + speech permissions asked on first mic tap, in context.
  • Transcript → same AI parse endpoint as S6 (voice is just another keyboard) → confirmation card, mandatory tap/say-yes. Parse-endpoint hardening for noisy voice input is in HT-1002's scope.

Verification

  • Dev-client builds install and run on both physical devices
  • 20-phrase test script: parse-to-confirm accuracy measured (target ≥95% at confirm screen)
  • Permission denial → mic button explains and falls back to typing
Exit: "Remind me to drink water every two hours at work" → correct confirmed habit.

Sprint 10 — Voice check-in & languages Phase 38 pts

Goal: small-vocabulary, high-reliability voice check-in; Arabic + English verified.

Stories

HT-1003 Voice check-in: done/skip/snooze (3) HT-1004 TTS confirmation read-back, off by default (2) HT-1005 Arabic/English recognition pass (3)

Technical notes

  • Check-in vocabulary is a fixed small set matched locally where possible — the AI parse is fallback, not first resort.
  • expo-speech TTS for eyes-free confirm; medication voice flows always require visual confirm (S7 rule).
  • Lighter sprint — buffer for EAS/build fallout from S9.

Verification

  • Done/skip/snooze via voice from today screen works on both platforms
  • Arabic phrase set tested with a native speaker (Nadeem/PoC group)
Exit: hands-busy check-in works reliably in both languages.

Sprint 11 — Health data: steps & workouts Phase 313 pts

Goal: the walk habit checks itself off — HealthKit + Health Connect, evaluated on-device.

Stories

HT-1101 HealthKit integration (5) HT-1102 Health Connect integration (5) HT-1103 On-device threshold → auto check-in (3)

Technical notes

  • Read-only, minimal datatypes: steps, distance, workouts. Threshold check runs on the phone; backend receives only a normal check-in event (source: auto_health). Raw samples never leave the device.
  • Permission asked only when a user links a specific habit to a data type ("Auto-track from steps?"). Denial → manual fallback, no dead ends.
  • Evaluation on app open + background fetch where the OS allows; catch-up evaluation covers missed background windows.

Verification

  • Walk 8k steps → habit auto-completes on both platforms; dashboard marks source as auto
  • Revoke permission in OS settings → app degrades gracefully to manual
  • Network inspection: no health payloads in any API call
Exit: step-based habits complete themselves for a full week without manual input.

Sprint 12 — Sleep, mindfulness, assistant & store prep Phase 315 pts

Goal: finish auto-tracking, ship the grounded conversational assistant, clear store review. Phase 3 ships at sprint end.

HT-1104 Sleep + mindfulness auto-tracking (3) HT-1105 Permission flow polish + fallbacks (2) HT-1106 Privacy policy + store declarations (2) HT-707 Conversational assistant, text + voice (8)

  • Guardrail suite extended with assistant red-team cases (dosage bait, diagnosis bait) — zero violations

  • Store review passed (or submitted with tracked follow-ups)
Exit: Phase 3 gate measurement: auto-tracked vs. manual retention; voice accuracy stats.
🚧 Phase 3 gate: auto-tracked habits show higher 30-day retention than manual equivalents · voice parse ≥95% at confirm · store review cleared.

🔴 Phase 4 — Guidance & Polish Sprints 13–15

Sprint 13 — Wellness suggestion library Phase 411 pts

Goal: "AI picks from a vetted menu, never cooks" — dietary & exercise ideas as habit-sized cards.

Stories

HT-1201 Vetted library + review workflow (5) HT-1202 "Ideas for you" gallery + disclaimers (3) HT-1203 AI vetted-menu selection (3)

Technical notes

  • Library items are human-reviewed content rows; the AI may only select and schedule from them (by ID) — it cannot generate novel dietary/exercise text. Enforced by schema: the coach returns library IDs, not strings.
  • Persistent non-dismissable disclaimer footer on every suggestion surface.
  • Filtering by lifestyle answers only — never by medical data (we don't collect any).

Verification

  • Schema test: coach responses referencing non-existent library IDs are rejected
  • Disclaimer present on every surface, both platforms
Exit: fitness/energy-goal users see relevant, safe, vetted ideas.

HT-1301 Ramadan mode (5) HT-1302 Prayer anchors + calculation-method setting (3) HT-1303 Arabic content pass (3)

  • RTL rendering clean on all habit screens
